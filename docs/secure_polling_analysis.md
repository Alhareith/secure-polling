# التحليل الهندسي والأمني لمنصة «صَوِّت»

## 1. قرار التقنية قبل التنفيذ

يعتمد المشروع **Flask** مع صفحات خادم خفيفة باستخدام Jinja، و**SQLite** للنسخة المحلية الأولى، وواجهة ويب قابلة للاستخدام من الهاتف والحاسوب. اختيار Flask مقصود؛ فالنظام يحتاج نماذج HTML، وجلسة مشرف تقليدية، ومسارات محدودة وواضحة، وليس واجهة API عالية التزامن أو تطبيقًا لحظيًا معقدًا. FastAPI ممتاز لواجهات JSON والخدمات غير المتزامنة، لكنه سيضيف قرارًا معماريًا إضافيًا بين واجهة أمامية مستقلة وخادم API من دون فائدة حاسمة في هذا النطاق.

> **القرار المعتمد:** Flask هو الإطار الأنسب للنسخة الأولى. تستخدم SQLAlchemy 2.0 داخل طبقة البنية التحتية فقط، وتبقى SQLite قاعدة بيانات محلية للتسليم الأكاديمي والتشغيل المفرد، لا قاعدة بيانات نشر عام متعدد المثيلات.

> **حالة المراجعة:** اعتمد المستخدم في جلسة المراجعة قرارات Flask وJinja وSQLite والجلسة الخاصة بالمشرف والنطاق المغلق والمختبر الأكاديمي المنفصل في 23 أغسطس 2026.

تسمح SQLite بقراءات متزامنة كثيرة، لكنها تسمح بكاتب واحد فقط في اللحظة الواحدة؛ لذلك تصلح للنسخة المحلية بشرط معاملات قصيرة، وتفعيل WAL و`busy_timeout`. عند الحاجة إلى تشغيل عام أو عدة مثيلات أو ذروة كتابة مرتفعة، يجب ترحيل تنفيذ المستودعات إلى PostgreSQL [1].

| قرار | يعتمد | يستبعد |
|---|---|---|
| الإطار | Flask + Jinja + Blueprints | SPA منفصلة أو FastAPI في النسخة الأولى |
| قاعدة البيانات | SQLite محلية، ملف واحد، عملية واحدة | SQLite موزعة أو PostgreSQL في النسخة الأولى |
| الدخول | حساب للمشرف وجلسة خادم | حساب أو اسم أو بريد للمصوّت |
| الحماية التشغيلية | AES-GCM، HMAC-SHA256، RSA-PSS، SHA-256 | Caesar أو DES3 في مسار التصويت الحقيقي |
| نطاق الاستخدام | استطلاعات مغلقة صغيرة إلى متوسطة | انتخابات رسمية أو سياسية أو عامة |
| الخصوصية | فصل بين أهلية الرمز والبطاقة المخزنة | ادعاء إخفاء مجهول مطلق ضد الخادم نفسه |

## 2. حد النطاق الصارم

المشروع نظام **استطلاع داخلي مغلق** للصفوف والنوادي وفرق العمل والمبادرات الصغيرة. يفترض وجود مجموعة مؤهلة يحددها المشرف، من دون أن تُخزَّن أسماء تلك المجموعة بجوار بطاقات التصويت.

النطاق الأولي هو حتى **200 رمز مؤهل** لكل استطلاع مع ذروة لا تتجاوز **5 طلبات تصويت صحيحة في الثانية** على عملية Flask واحدة. هذه أرقام قبول هندسية يجب اختبارها، وليست ضمانًا عامًا. عند تجاوزها يصبح الانتقال إلى PostgreSQL قرارًا إلزاميًا.

| داخل النطاق | خارج النطاق |
|---|---|
| اختيار واحد، متعدد بحد أقصى، أو نعم/لا | انتخابات حكومية أو سياسية |
| رمز عشوائي لمرة واحدة | تصويت مجهول تشفيريًا ضد مشغل خادم خبيث |
| إغلاق تلقائي أو يدوي، ثم عد وتقرير | تطبيق هاتف أصلي أو إشعارات فورية |
| تقرير تدقيق موقّع وسجل أحداث | Blockchain أو خادم موزع |
| مختبر أكاديمي للخوارزميات | تصويت مفتوح بلا قائمة أهلية |

## 3. تعريف المشكلة ومعيار النجاح

المجموعة تحتاج لاتخاذ قرار من دون ضغط اجتماعي أو تكرار أو كشف اختيارات الأفراد. التصويت الورقي قد يحقق بعض السرية لكنه لا يسهل التوزيع أو التدقيق، والاستطلاع المفتوح يسهل تكراره أو ربطه بصاحبه.

لا يعني نجاح المشروع أنه «غير قابل للاختراق». النجاح هو أن يحقق المتطلبات المعلنة: يمنع الاستخدام العادي المتكرر للرمز، ولا يخزن صلة مباشرة بين الرمز والاختيار، ويكشف التعديل في السجل أو التقرير، ويعرض حدوده بوضوح.

## 4. الأطراف والمسؤوليات

| الطرف | ما يفعله | ما لا يجوز أن يراه أو يفعله |
|---|---|---|
| المشرف | إنشاء الاستطلاع، إصدار الرموز، النشر، الإغلاق، قراءة النتيجة | ربط رمز مخزن باختيار فرد في الواجهة |
| المصوّت | فتح الرابط وإدخال الرمز وإرسال اختيار | إنشاء حساب أو رؤية نتائج مخفية أو إعادة استخدام الرمز |
| المراجع | فحص التقرير والتوقيع وحالة السجل | رؤية رمز أو بطاقة أو اختيار فردي |
| النظام | فحص الوقت والحالة والرمز، تشفير البطاقة، العد | حفظ اسم أو بريد أو IP داخل بطاقة التصويت |

## 5. نموذج الخصوصية وحدوده

يفصل النظام بين جدول الرموز وجدول البطاقات، فيمنع وجود رابط **مخزن أو معروض** بينهما. لكن طلب التصويت يصل إلى الخادم حاملاً الرمز والاختيار في العملية نفسها؛ لذلك لا يجوز الادعاء بأن مشغّل خادم خبيث لا يستطيع الربط بينهما أثناء المعالجة أو من السجلات السيئة الإعداد.

> **الادعاء الصحيح:** المنصة لا تخزن صلة مباشرة بين الرمز والبطاقة، ولا تطلب هوية المصوّت، ولا تعرض اختيارات الأفراد؛ لكنها لا تحقق إخفاء هوية تشفيريًا ضد الخادم ذاته.

> **حالة المراجعة:** اعتمد المستخدم نموذج الخصوصية أعلاه، بما في ذلك هذا القيد الصريح، في 23 أغسطس 2026.

إذا صار مطلوبًا منع الربط حتى عن مشغّل الخادم، نحتاج تغييرًا معماريًا كبيرًا مثل فصل خادم الأهلية عن خادم الصندوق أو استخدام blind signatures أو mixnets. لا يدخل ذلك في النسخة الأولى.

## 6. دورة حياة الاستطلاع

تستخدم المنصة آلة حالات صريحة، ولا تعتمد على مجموعة أعلام مبعثرة.

| الحالة | المعنى | العمليات المسموحة | الانتقال التالي |
|---|---|---|---|
| `DRAFT` | غير منشور | تعديل السؤال والخيارات والقواعد | نشر أو إلغاء |
| `PUBLISHED` | موقّع ومقفّل وقبل البداية | إصدار أو إلغاء الرموز قبل الفتح | فتح أو إلغاء |
| `OPEN` | التصويت متاح | قبول بطاقة صالحة فقط | إغلاق يدوي أو تلقائي |
| `CLOSED` | لا بطاقات جديدة | تدقيق وعد | إصدار النتيجة |
| `TALLIED` | تقرير نهائي موقّع | عرض التقرير والتحقق | أرشفة |
| `CANCELLED` | استطلاع ملغى | عرض السبب | لا انتقال |
| `ARCHIVED` | منتهٍ ومحفوظ | قراءة التقرير فقط | لا انتقال |

تقفل بعد النشر: السؤال، والخيارات، ونوع التصويت، والحد الأعلى للاختيارات، وبداية ونهاية النافذة، وقواعد ظهور النتيجة. أي تعديل لاحق يعني إنشاء استطلاع جديد.

> **حالة المراجعة:** اعتمد المستخدم دورة الحياة وقفل الإعدادات بعد النشر في 23 أغسطس 2026.

## 7. مسار البيانات والتشفير

### الرموز

ينشئ النظام رمزًا عشوائيًا باستخدام `secrets.token_urlsafe(32)` أو ما يعادله. لا يخزن الرمز الخام بعد العرض أو التصدير؛ بل يخزن `HMAC-SHA256(token, token_pepper)` مع `poll_id` والحالة. HMAC أقوى من التجزئة الساذجة عند تسرب القاعدة لأنه يحتاج إلى pepper خارج SQLite.

### قبول بطاقة التصويت

ينفذ القبول في معاملة SQLite قصيرة واحدة:

1. يتحقق من حالة الاستطلاع والنافذة الزمنية.
2. يحسب HMAC للرمز ويجد سجلًا بحالة `UNUSED`.
3. يتحقق من صحة الاختيار وفق نوع التصويت.
4. يشفر البطاقة بـ AES-256-GCM مع nonce فريد و`key_id`.
5. يدرج البطاقة في جدول مستقل لا يملك `token_id` أو `token_hmac`.
6. يغير حالة الرمز إلى `USED` بشرط ذري أن الحالة ما زالت `UNUSED`.
7. يضيف حدث تدقيق غير كاشف ويصدر إيصالًا عشوائيًا لا يعرض الاختيار.

إذا أخفقت خطوة واحدة، تتراجع المعاملة كاملة. لا تستهلك رمزًا بلا بطاقة، ولا تحفظ بطاقة بلا استهلاك رمز.

> **حالة المراجعة:** اعتمد المستخدم معاملة قبول التصويت الذرية وفصل الرمز عن البطاقة في 23 أغسطس 2026.

### الإغلاق والعد

بعد `CLOSED` فقط، تفك خدمة العد البطاقات وتتأكد من البنية و`poll_id` ونوع الاختيار. لا تحذف البطاقة الفاسدة؛ توسم `QUARANTINED` ويعرض التقرير عددها دون كشف محتواها. توقع النتيجة النهائية باستخدام RSA-PSS مع SHA-256.

### سجل التدقيق

كل حدث إداري أو نظامي يملك `previous_hash` و`event_hash`. سلسلة التجزئة تكشف التعديل ضمن النسخة المخزنة، لكنها لا تمنع مشغّل القاعدة الخبيث من إعادة بنائها. لذلك يوقّع النظام التقرير النهائي ويحفظ أو يصدر نسخة منه خارج قاعدة البيانات. التوقيع الرقمي يقدم تحققًا من أصل البيانات وسلامتها عند استخدامه بصورة صحيحة [2].

## 8. نموذج التهديدات والضوابط

| التهديد | الضبط المطلوب | الحد المتبقي |
|---|---|---|
| استخدام الرمز مرتين | تحديث ذري ومعاملة واحدة وحالة `UNUSED` | لا يمنع سرقة الرمز قبل استخدام صاحبه |
| تخمين الرموز | 256-bit tokens، HMAC، rate limiting، رسالة خطأ عامة | لا يحمي رمزًا كشفه صاحبه |
| CSRF للمشرف | CSRF token، SameSite، إعادة تحقق حساسة | لا يحمي جهاز مشرف مصابًا |
| XSS | Jinja auto-escape، CSP، منع HTML غير موثوق | يحتاج مراجعة كل قالب جديد |
| clickjacking | `frame-ancestors 'none'` وX-Frame-Options | لا يغني عن CSRF |
| تعديل قاعدة البيانات | AES-GCM، hash chain، توقيع تقرير، نسخ احتياطية | لا يحمي من مشغل يملك المفاتيح |
| كشف النتائج مبكرًا | منع العد والعرض قبل الإغلاق | لا يمنع المشرف ذا الامتياز من إساءة استخدام بيئة التشغيل |
| تسريب مفتاح AES | مفاتيح خارج SQLite، key IDs، تدوير | ليس نظام إدارة مفاتيح مؤسسيًا |
| تعطيل الخدمة | حدود طلبات وrate limits ومهلات | لا مقاومة كاملة لـ DDoS عام |
| خطأ وقت الخادم | UTC مصدره الخادم | يتطلب ضبط ساعة الخادم |

توصي وثائق Flask بتطبيق حماية CSRF صريحة مع الجلسات القائمة على ملفات الارتباط، وبمراجعة CSP وHSTS وخيارات `Secure` و`HttpOnly` و`SameSite` [3].

## 11. نموذج البيانات المفاهيمي

| الكيان | الحقول الجوهرية | القيد الأمني |
|---|---|---|
| `Administrator` | id، username، password_hash، role، timestamps | لا كلمة مرور خام |
| `Poll` | id، title، question، type، state، starts_at، ends_at، configuration_hash، signature | يقفل بعد النشر |
| `PollOption` | id، poll_id، label، display_order | لا تعديل بعد النشر |
| `VoterToken` | id، poll_id، token_hmac، status، issued_at، used_at، revoked_at | لا FK إلى Ballot |
| `Ballot` | id، poll_id، ciphertext، nonce، tag، key_id، ciphertext_hash، receipt_hmac، submitted_at، status | لا رمز ولا هوية |
| `AuditEvent` | id، poll_id، event_type، payload_digest، previous_hash، event_hash، occurred_at | لا رمز خام ولا اختيار |
| `ResultReport` | id، poll_id، totals، report_hash، signature، key_id، created_at | موقّع وغير قابل للتعديل |
| `CryptoKeyMetadata` | key_id، purpose، algorithm، created_at، retired_at | المفتاح الخاص خارج SQLite |

العلاقات: الاستطلاع يملك الخيارات والرموز والبطاقات والأحداث والتقرير. **لا توجد علاقة بيانات بين `VoterToken` و`Ballot`.**

## 12. المعمارية الطبقية وقواعد الاعتماد

```text
Presentation  ->  Application  ->  Domain
                        |
                        v
                 Infrastructure
```

| الطبقة | مسؤوليتها | ما لا تعرفه |
|---|---|---|
| العرض | Flask routes، النماذج، HTTP، رسائل المستخدم | SQL والتشفير والعد |
| التطبيق | حالات الاستخدام والمعاملات والصلاحيات | Jinja أو SQLite |
| المجال | الكيانات والحالات والسياسات والعقود | Flask وSQLAlchemy |
| البنية التحتية | SQLite، التشفير، الجلسات، الساعة، logging | قرارات واجهة المستخدم |

قواعد صارمة: لا ينفذ route SQL أو تشفيرًا أو عدًا؛ لا تستورد طبقة المجال أي مكتبة ويب أو قاعدة بيانات؛ لا تستخدم وحدة المختبر الأكاديمي في المسار التشغيلي؛ ولا توضع المفاتيح الخاصة داخل الجداول.

## 15. خطة الاختبارات

| مستوى الاختبار | الحالات الإلزامية |
|---|---|
| المجال | انتقال الحالات، قفل الإعداد، قواعد الخيارات |
| التطبيق | إصدار/إلغاء الرمز، rollback، العد |
| التشفير | tag خاطئ، تقرير معدل، nonce فريد |
| المستودعات | شرط التحديث الذري وعزل المعاملة |
| المسارات | منع غير المشرف، CSRF، قفل النتائج |
| إساءة الاستخدام | إرسالان متزامنان لنفس الرمز، XSS في السؤال، وقت منتهٍ، تعديل قاعدة تجريبية |
| قبول | مشرف ينشئ استطلاعًا و40 رمزًا و31 بطاقة ثم تقرير تدقيق |

## 16. قرارات لا يجوز تجاوزها قبل التنفيذ

1. النسخة الأولى محلية/تعليمية؛ لا تنشر SQLite على ملفات مؤقتة أو أكثر من مثيل واحد.
2. الخصوصية مفصولة تخزينيًا وواجهاتيًا، وليست إخفاء هوية ضد الخادم نفسه.
3. لا يوجد أي FK أو سجل أو log يربط `VoterToken` بـ `Ballot`.
4. لا يسمح بتعديل التصويت بعد الإرسال في النسخة الأولى.
5. توزع الرموز خارج المنصة؛ لا بريد إلكتروني ولا SMS في النسخة الأولى.
6. Diffie-Hellman والخوارزميات الكلاسيكية وDES3 مختبرية فقط.
7. التقرير النهائي الموقّع هو نقطة التحقق الأساسية؛ Hash Chain ليست بديلاً عن التوقيع.
