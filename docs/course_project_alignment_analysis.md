# تحليل مواءمة مقرر أمن المعلومات مع مشروع «صوّت»

| الحقل | القيمة |
|---|---|
| المقرر | أمن المعلومات — المستوى الرابع، تقنية معلومات |
| المشروع | «صوّت»: منصة استطلاعات سرية قابلة للتدقيق |
| حالة المشروع عند المراجعة | **تحليل ومواصفات متقدمة؛ لا توجد منصة تصويت منفذة بعد** |
| مصادر التحليل | مواد مختبرات المقرر، والتحليل الهندسي، ووثيقة SRS داخل المشروع |
| الغرض | تحويل موضوعات المختبر إلى مخرجات مشروع عملية، آمنة، وقابلة للشرح والتقييم |

## الملخص التنفيذي

محتوى المقرر يبدأ بمفاهيم علم التشفير ومثلث الأمان، ثم ينتقل إلى التشفير المتماثل وغير المتماثل، ويستخدم خوارزميات **Caesar** و**Monoalphabetic** و**Vigenère** لتعليم منطق الاستبدال، المفتاح، الحساب المعياري، ودوال التشفير وفك التشفير. وتعرض المادة أيضاً **AES** و**RSA** و**Diffie–Hellman** ضمن خريطة الخوارزميات؛ لذلك ينسجم مشروع «صوّت» مع المقرر عندما يفصل بوضوح بين المختبر التعليمي وبين حماية منصة التصويت الفعلية.[1] [2]

المشروع مكتمل من ناحية **التحليل الأمني والمتطلبات**: فهو يحدد نطاقاً مغلقاً غير انتخابي، ويفصل بين أهلية الرمز وبطاقة التصويت، ويقترح AES-GCM لسرية البطاقات، وHMAC-SHA256 لحماية بصمات الرموز، وRSA-PSS لتوقيع التقرير النهائي. إلا أنه ليس مكتمل التنفيذ: شجرة Flask محجوزة كهيكل فقط، وواجهة التطبيق الحالية صفحة مثال، وواجهة الخادم ونموذج البيانات لا يحتويان بعد على كيانات الاستطلاعات أو الرموز أو البطاقات أو التدقيق.[3]

> **النتيجة الأساسية:** المشروع مناسب جداً بوصفه مشروعاً تطبيقياً للمقرر، بشرط أن تبقى خوارزميات التشفير الكلاسيكية وDES3 داخل مختبر أكاديمي منفصل، وألا تُقدَّم على أنها حماية كافية لبطاقات التصويت أو للبيانات التشغيلية.

## 1. خريطة نواتج تعلم المقرر

| محور المقرر | الدليل من المواد | الناتج التعليمي المقترح داخل المشروع | أسلوب التقييم |
|---|---|---|---|
| مفاهيم علم التشفير ومثلث الأمان | مختبر 1 يقدّم التعريفات والسرية والسلامة والأصالة | صفحة مفاهيم تشرح أين تتحقق السرية والسلامة والأصالة في المنصة | يفسّر الطالب وظيفة كل آلية دون خلط بين المصطلحات |
| التشفير المتماثل وغير المتماثل | مختبر 1 يميّز بين النمطين | AES-GCM لتشفير البطاقة، وRSA-PSS لتوقيع التقرير | يربط الطالب المفتاح والهدف ومرحلة الاستخدام بصورة صحيحة |
| Caesar Cipher | مختبر 2 يشرح الإزاحة والحساب المعياري | تجربة مستقلة تُظهر التحويل وحساب `(P + k) mod 26` | اختبار تشفير وفك النص `HELLO` بمفتاح 3 إلى `KHOOR` ثم الاسترجاع |
| Monoalphabetic Cipher | مختبر 3 يشرح جدول الاستبدال الثابت | تجربة مستقلة تقبل مفتاح استبدال كاملاً وتتحقق من كونه تبديلًا فريداً | يبين الطالب أثر التكرار ولماذا يسهل تحليل التردد كسره |
| Vigenère Cipher | مختبر 4 ودليل Tkinter يشرحان المفتاح المتكرر وعمليتي التشفير وفك التشفير | تجربة تفاعلية تعرض النص والمفتاح الممتد والنتيجة | اختبار `ATTACK + LEMON → LXFOPV` ثم فكها بصورة صحيحة |
| البرمجة المنظمة وواجهة المستخدم | دليل Vigenère يربط مربعات الإدخال بالدوال والنتائج | فصل دوال الخوارزمية عن مكونات الواجهة، مع تحقق مدخلات ورسائل عربية | مناقشة مسار البيانات: إدخال ← دالة ← نتيجة |
| AES وRSA وDiffie–Hellman | مختبر 1 يسردها ضمن الخوارزميات المهمة | توضيح الفرق بين التشفير، التوقيع، والتبادل في صفحة التعلم | لا يوصف SHA-256 كتشفير، ولا Diffie–Hellman كتشفير رسالة |

## 2. مواءمة وظائف «صوّت» مع المفاهيم الأمنية

| هدف أمني | آلية مخططة في المواصفات | ما يتعلمه الطالب | قيد يجب شرحه |
|---|---|---|---|
| سرية بطاقة التصويت | AES-256-GCM مع nonce فريد وAAD | الفرق بين التشفير المتماثل وسلامة النص المشفر | لا يكفي تشفير النص وحده إذا أُسيء التعامل مع المفاتيح أو الـ nonce |
| أهلية التصويت ومنع الاستخدام المتكرر | رمز عشوائي لمرة واحدة مع HMAC-SHA256 وتحديث ذري للحالة | الفرق بين الرمز الخام وبصمته المجهزة للتحقق | حماية الرمز لا تمنع سرقته قبل استخدام صاحبه |
| سلامة التقرير وأصالته | تجزئة التقرير وتوقيعه بـ RSA-PSS وSHA-256 | الفرق بين التجزئة والتوقيع الرقمي | سلسلة التجزئة لا تحل محل توقيع نهائي محفوظ خارج قاعدة البيانات |
| الخصوصية التخزينية | عدم وجود رابط بين `VoterToken` و`Ballot` | تقليل جمع البيانات وفصل الصلاحية عن الاختيار | لا يعني ذلك مجهولية تشفيرية مطلقة ضد خادم خبيث |
| قابلية التدقيق | سجل أحداث متسلسل وتقرير نهائي قابل للتحقق | أدلة النزاهة وحدودها | لا يجوز أن يحتوي السجل على رمز خام أو اختيار فردي |
| الاستخدام المسؤول | نطاق استطلاعات داخلية مغلقة فقط | بناء نظام وفق حدود معلنة | لا يُستخدم المشروع لانتخابات رسمية أو سياسية |

التوقيعات الرقمية تُستخدم للتحقق من مصدر البيانات وسلامتها، بينما تقترح وثائق Flask ضبط حماية الجلسات وCSRF وسياسات محتوى مناسبة للتطبيقات المبنية على ملفات الارتباط.[4] [5] وتوضح وثائق SQLite أن ملاءمتها تكون في سيناريوهات محددة؛ لذلك لا يُنشر تصميم SQLite المحلي على بيئة متعددة المثيلات أو نظام ملفات مؤقت.[6]

## 3. الحالة الفعلية للمشروع والفجوات

| المجال | الموجود الآن | الحالة | الأثر |
|---|---|---|---|
| التحليل الأمني | وثيقة `secure_polling_analysis.md` تغطي النطاق والتهديدات ودورة الحياة والتشفير والاختبارات | مكتمل تحليلياً | أساس قوي للتنفيذ، لكنه لا يشغّل وظيفة فعلية |
| المتطلبات | وثيقة SRS تتضمن متطلبات FR وNFR وتسلسل P0–P8 | مكتمل تحليلياً | توفر معايير قبول واضحة لكل مرحلة |
| الجزء التعليمي | توصيف واضح لمختبر مستقل للخوارزميات | مصمم فقط | لا توجد صفحة أو دوال خوارزميات منفذة |
| تطبيق Flask | مجلدات طبقية وملفات محجوزة | هيكل فارغ | لا يوجد factory أو routes أو مستودعات أو تشفير أو اختبارات Python |
| واجهة الويب الحالية | صفحة React افتراضية باللغة الإنجليزية | نموذج قالب | لا تقدم تجربة التصويت أو المختبر أو واجهة عربية |
| الخادم وقاعدة البيانات | مصادقة القالب وجدول `users` فقط | غير مرتبط بالمواصفات | لا توجد جداول `polls` أو `voter_tokens` أو `ballots` أو `audit_events` أو `result_reports` |
| الاختبارات | اختبار خروج القالب فقط | غير كافٍ | لا يوجد اختبار دورة الحالة أو الذرية أو التزامن أو التشفير أو التدقيق |

## 4. فجوات الأولوية قبل بناء الواجهة

البدء بواجهة للتصويت أو مختبر للخوارزميات قبل تثبيت النموذج التنفيذي سيخالف تسلسل SRS ويجعل التحقق الأمني أصعب. الأولوية الصحيحة هي تثبيت قرار التقنية، ثم بناء قواعد المجال واختبارها، ثم البيانات والمعاملات، ثم تدفقات المشرف والمصوّت، وأخيراً واجهة الاستخدام والمختبر التعليمي.

| الأولوية | المخرج المطلوب | معيار الإنجاز |
|---|---|---|
| P0 | اعتماد مسار تنفيذي واحد وتحديث الوثائق عند الحاجة | لا يوجد تعارض بين التقنية الموثقة والتقنية التي سيعمل بها التطبيق |
| P1 | حالات `PollState`، قواعد الخيارات، وقواعد الانتقال | اختبارات الوحدة تمنع الانتقالات والتكوينات غير الصحيحة |
| P2 | نموذج البيانات، المستودعات، ومعاملة قبول بطاقة ذرية | لا تقبل محاولتان متزامنتان بطاقتين للرمز نفسه |
| P3 | مصادقة المشرف، CSRF، رؤوس الحماية، وتقييد المحاولات | اختبارات رفض الطلبات غير المصرح بها أو غير المحمية |
| P4 | إنشاء الاستطلاع، النشر، قفل الإعدادات، وتوليد الرموز | لا يمكن تعديل إعداد منشور ولا استرجاع رمز خام سابق |
| P5 | AES-GCM وHMAC والإيصال | تفشل قراءة البطاقة المعدلة ولا يظهر الرمز أو الاختيار في السجلات |
| P6 | العد، العزل، السجل، والتقرير الموقّع | يفشل التحقق بعد تعديل التقرير |
| P7 | واجهة عربية متجاوبة يمكن الوصول إليها | إتمام التصويت في ثلاث شاشات، من دون نتائج مبكرة |
| P8 | مختبر الخوارزميات | يثبت الاختبار انفصاله عن المفاتيح والبطاقات والجداول التشغيلية |

## 5. القرار المعماري الذي يحتاج إلى حسم

يوجد تعارض جوهري يجب حسمه قبل تنفيذ الوظائف: وثائق المشروع تعتمد **Flask + Jinja + SQLite محلية**، بينما التطبيق المرفق يعمل حالياً بقالب **React + tRPC + Express + MySQL**. لا يصح بناء نصف النظام في كل مسار؛ لأن ذلك سيكرر قواعد الأعمال ويعرّض فصل البيانات واختبارات الذرية للخطر.

| البديل | متى يختار | العمل المطلوب | النتيجة التعليمية |
|---|---|---|---|
| **أ. مسار Flask المحلي** | إذا كان التسليم المطلوب تطبيق Python/Flask محلياً ومتوافقاً حرفياً مع وثيقة SRS الحالية | تنفيذ مراحل P1–P8 داخل `flask_polling` مع SQLite محلية؛ ويظل التطبيق المرفق واجهة شرح أو يُستبعد من التسليم التنفيذي | أقرب إلى التصميم الموثق وإلى نماذج Python في المختبرات |
| **ب. مسار تطبيق الويب المرفق** | إذا كان المطلوب تطبيق ويب يعمل داخل هذا المشروع المُدار | تعديل SRS والتحليل لاستبدال Flask/SQLite بـ React/tRPC/MySQL، ثم تنفيذ المتطلبات في المخطط وطبقة الخادم والواجهة | تجربة ويب متكاملة، لكن بقرار تقني جديد يجب توثيقه واختباره |

> **التوصية التعليمية:** اختر المسار **أ** إن كانت مادة التقييم تشترط Python أو Flask، واختر المسار **ب** إن كانت الأولوية هي تسليم تطبيق الويب المرفق. في الحالتين يجب أن يبقى مختبر Caesar وMonoalphabetic وVigenère معزولاً تماماً عن تشفير بطاقة التصويت الحقيقي.

## 6. حدود يجب إبقاؤها ظاهرة في العرض والمناقشة

| العبارة الصحيحة | العبارة التي يجب تجنبها |
|---|---|
| «المنصة تفصل الرمز عن البطاقة في التخزين والواجهة.» | «المنصة مجهولة تماماً حتى أمام مشغّل الخادم.» |
| «AES-GCM هو المسار التشغيلي لحماية البطاقة.» | «Caesar أو Vigenère أو DES3 يكفيان لحماية التصويت.» |
| «التقرير الموقّع يساعد على كشف تعديل محتواه بعد إصداره.» | «سلسلة التجزئة وحدها تمنع كل تعديل من مشغّل قاعدة البيانات.» |
| «المنصة استطلاع داخلي أكاديمي محدود النطاق.» | «المنصة صالحة لانتخابات رسمية أو سياسية.» |
| «Diffie–Hellman آلية لتأسيس سر مشترك، لا لتشفير الرسالة مباشرة.» | «Diffie–Hellman خوارزمية تشفير للرسائل.» |

## 7. مخرجات مقترحة للتسليم الأكاديمي

ينبغي أن يتضمن التسليم النهائي وثيقة المتطلبات، مخطط المعمارية، نموذج البيانات مع إبراز غياب أي رابط بين الرمز والبطاقة، مخطط دورة حياة الاستطلاع، لقطات لواجهات المشرف والمصوّت والتدقيق والمختبر، وخطة اختبار تغطي التزامن، التشفير، التوقيع، السجلات، وإساءة الاستخدام. أثناء المناقشة، يُفضل تنفيذ تجربة Vigenère المعتمدة (`ATTACK` و`LEMON`) ثم توضيح لماذا لا تستخدم هذه التجربة في البطاقة التشغيلية، وعرض كيف يتحقق التقرير الموقّع من التعديل.
