# خارطة تنفيذ منصة «صَوِّت»

> **الحالة:** خطة تنفيذ معتمدة من المستخدم في 23 أغسطس 2026. لا تمثل هذه الوثيقة كودًا أو بدءًا للتنفيذ، بل تحدد الترتيب الذي يمنع التداخل بين الطبقات والخوارزميات والواجهة.

## 1. مبدأ التنفيذ

يُبنى المشروع من الداخل إلى الخارج، لا من الواجهة إلى قاعدة البيانات. أي إننا نبدأ بقواعد الاستطلاع، ثم التخزين، ثم الحماية، ثم Flask، ثم الواجهة. السبب أن واجهة جميلة فوق قواعد غير مختبرة تجعل إصلاح الأخطاء لاحقًا صعبًا ومكلفًا، خصوصًا في نظام يتعامل مع الخصوصية والتدقيق.

```text
قواعد النظام → البيانات → الحماية → Flask → الواجهة → التدقيق → المختبر → التحقق النهائي
```

لا تبدأ مرحلة إلا بعد اجتياز **بوابة انتقال** واضحة. وإذا فشلت اختبارات مرحلة، نصلح المرحلة نفسها ولا نضيف ميزة فوقها.

| المبدأ | التطبيق العملي |
|---|---|
| وظيفة واحدة في كل مرة | لا نضيف صفحة أو خوارزمية أو جدولًا لا يخدم المرحلة الحالية |
| طبقة واحدة مسؤولة | لا تكتب Flask تشفيرًا، ولا تنفذ الواجهة SQL، ولا تعرف `core` تفاصيل SQLite |
| الاختبار مع الميزة | كل وظيفة تملك اختبار نجاح، واختبار فشل، واختبار إساءة استخدام عند الحاجة |
| التوسع المتأخر | لا نضيف QR أو شبكة محلية أو عدة مشرفين أو PostgreSQL قبل اكتمال النواة |
| فصل التعليمي عن التشغيلي | المختبر الأكاديمي لا يصل إطلاقًا إلى بطاقات أو رموز أو مفاتيح التصويت الفعلية |

## 4. المرحلة 1 — تهيئة Flask وبيئة Python

### الهدف

تحويل الهيكل الفارغ إلى مشروع Python نظيف قابل للتشغيل والاختبار محليًا، من دون أي منطق تصويت أو واجهة نهائية.

### الملفات التي تملأ لأول مرة

| الملف | المهمة المحددة |
|---|---|
| `flask_polling/pyproject.toml` | تحديد Python والحزم المقيدة بالإصدارات وأوامر الاختبار |
| `flask_polling/run.py` | نقطة تشغيل محلية فقط |
| `src/web/app.py` | Application Factory وإعدادات البيئة |
| `src/web/__init__.py` | تعريف حزمة Flask فقط |
| `tests/unit/` | اختبار إنشاء التطبيق وإعدادات الاختبار |

### ما يدخل

Flask، SQLAlchemy، Alembic أو Flask-Migrate، `cryptography`، Argon2، `pytest`، و`pytest-cov` فقط. كما ينشأ ملف إعداد منفصل لبيئات `development` و`testing` و`production`، من دون أسرار داخل المشروع.

### ما لا يدخل

لا قاعدة بيانات فعلية، ولا صفحة دخول، ولا نموذج استطلاع، ولا خوارزمية تشفير، ولا CSS نهائي.

### اختبارات البوابة

1. إنشاء Flask بالتكوين التطويري والاختباري ينجح.
2. Debug لا يعمل في وضع الإنتاج.
3. أسرار الجلسات والمفاتيح تقرأ من البيئة فقط.
4. تشغيل `pytest` ينجح ولو على اختبارات التهيئة فقط.

## 5. المرحلة 2 — قلب النظام وقواعد الأعمال

### الهدف

كتابة القواعد التي لا تعتمد على Flask أو SQLite. هذه هي أكثر مرحلة تمنع التلخبط لاحقًا، لأن كل شاشة وكل جدول يجب أن يلتزم بما تقرره هذه الطبقة.

### الملفات المستهدفة

| الملف | ما يضاف لاحقًا |
|---|---|
| `src/core/polls.py` | حالات `DRAFT` و`PUBLISHED` و`OPEN` و`CLOSED` و`TALLIED` و`ARCHIVED` و`CANCELLED` وقواعد الانتقال |
| `src/core/tokens.py` | حالات الرمز وقاعدة الاستخدام الواحد |
| `src/core/audit.py` | شكل حدث التدقيق وقواعد سلسلة البصمات |
| `tests/unit/` | اختبارات القواعد من دون شبكة أو قاعدة بيانات |

### ترتيب التنفيذ داخل المرحلة

1. تعريف أنواع التصويت الثلاثة وقواعد الاختيارات.
2. تعريف حالة الاستطلاع وانتقالاتها المسموحة فقط.
3. تعريف حالة الرمز وانتقالاته المسموحة فقط.
4. تعريف شكل بطاقة التصويت المنطقي بلا تشفير بعد.
5. تعريف أحداث التدقيق المنطقية.

### اختبارات البوابة

| الاختبار | النتيجة المطلوبة |
|---|---|
| نشر مسودة صحيحة | يتحول الاستطلاع إلى `PUBLISHED` |
| تعديل استطلاع منشور | يرفض دائمًا |
| إغلاق استطلاع مفتوح | يسمح مرة واحدة فقط |
| استعمال رمز مستخدم | يرفض دائمًا |
| اختيار خارج حدود التصويت | يرفض في القواعد لا في الواجهة فقط |

**لا ننتقل إلى البيانات قبل أن تكون هذه الاختبارات خضراء بالكامل.**

## 7. المرحلة 4 — الحماية التشغيلية

### الهدف

بناء الحماية التي يحتاجها مسار التصويت الحقيقي، قبل أن نفتح أي مسار ويب لقبول صوت.

### الملفات المستهدفة

| الملف | ما يضاف لاحقًا |
|---|---|
| `src/crypto/secure.py` | SHA-256 وHMAC-SHA256 وAES-256-GCM وRSA-PSS |
| `src/crypto/keys.py` | قراءة المفاتيح وإصداراتها من البيئة أو تخزين مفاتيح محمي |
| `tests/unit/` | اختبارات صحة التشفير والتوقيع والتعديل |
| `tests/security/` | اختبارات العبث وإعادة nonce ومحاولات فك غير صالحة |

### ترتيب إضافة الحماية

1. مصدر عشوائية تشفيري للرموز والجلسات والإيصالات.
2. SHA-256 وHMAC لحماية بصمة الرمز والإيصال.
3. AES-GCM لتشفير بطاقة التصويت وفكها داخليًا.
4. إدارة `key_id` ونسخة مفتاح لكل عملية.
5. RSA-PSS لتوقيع التقرير النهائي والتحقق منه.
6. HKDF فقط إذا استخدم Diffie-Hellman لاحقًا في تجربة منفصلة.

### اختبارات البوابة

| الاختبار | النتيجة المطلوبة |
|---|---|
| تعديل ciphertext أو tag أو AAD | يفشل فك AES-GCM |
| تعديل التقرير الموقع | يفشل تحقق RSA-PSS |
| إدخال المفتاح أو pepper في السجل | يفشل اختبار Redaction |
| تكرار nonce مع `key_id` نفسه | يكتشف ويرفض |

> لا تضاف Caesar أو Vigenère أو DES3 أو بقية المختبر هنا؛ هذه مرحلة الحماية التشغيلية فقط.

## 8. المرحلة 5 — Flask والأمان الويبّي

### الهدف

ربط المكونات الآمنة السابقة بطلبات ويب مضبوطة، من دون بناء تجربة المستخدم النهائية بعد.

### الملفات المستهدفة

| الملف | ما يضاف لاحقًا |
|---|---|
| `src/web/app.py` | التسجيل المركزي للإعدادات وBlueprints والأخطاء والرؤوس |
| `src/web/auth.py` | تهيئة المشرف ودخوله وجلساته وخروجه وإعادة مصادقته |
| `src/web/routes.py` | مسارات أولية مفصولة بحسب الدور |
| `tests/security/` | CSRF والجلسات وrate limiting والرؤوس |

### عناصر المرحلة

1. حساب مشرف أول عبر تهيئة محلية، لا تسجيل عام.
2. Argon2id لكلمة المرور وجلسة خادم قصيرة.
3. CSRF لكل طلب يغير حالة.
4. رؤوس CSP وHSTS في HTTPS ومنع clickjacking.
5. حدود دخول المشرف وحدود تجريب رمز التصويت.
6. رسائل خطأ عامة لا تكشف هل الرمز خاطئ أو مستخدم أو ملغى.

### اختبارات البوابة

1. POST بلا CSRF يرفض.
2. محاولات الدخول تتعرض للحظر بعد الحد المحدد.
3. session منتهية لا تصل إلى مسار إداري.
4. headers المطلوبة موجودة في الاستجابات المناسبة.

### الهدف

مشرف مصادق عليه → إنشاء مسودة → تحقق قواعد core → حفظ → مراجعة → إعادة مصادقة → نشر وتوقيع → قفل

### اختبارات البوابة

3. تعديل حقل مقفل بعد النشر يفشل.
4. فتح التصويت يعتمد على UTC في الخادم، لا وقت المتصفح.

## 10. المرحلة 7 — الرموز ودخول المصوّت

### الهدف

إتاحة أهلية تصويت لمرة واحدة دون حساب أو اسم للمصوّت.

### مسار العمل

```text
المشرف يولد رموزًا → تظهر الرموز مرة واحدة → تحفظ بصماتها فقط
→ المصوّت يفتح رابط الاستطلاع → يرسل الرمز → يحصل على جلسة تصويت قصيرة
```

### نقاط الضبط

| القاعدة | التطبيق |
|---|---|
| لا حفظ للرمز الخام | نحفظ HMAC فقط |
| لا استهلاك مبكر للرمز | التحقق من الرمز لا يحوله إلى `USED` |
| لا كشف للحالة | رسالة موحدة للرمز الخاطئ أو المستخدم أو الملغى |
| لا حساب للمصوّت | session قصيرة لا تحمل هوية أو الرمز الخام |

### اختبارات البوابة

1. الرمز الصحيح في نافذة مفتوحة يفتح جلسة تصويت فقط.
2. الرمز لا يمكن استعماله خارج الاستطلاع أو النافذة.
3. الرمز المستخدم أو الملغى لا يكشف حالته للواجهة.
4. لا يظهر الرمز الخام في DB أو HTML أو logs.

## 11. المرحلة 8 — قبول بطاقة التصويت

### الهدف

تطبيق أهم تدفق في المشروع: الاختيار ثم التشفير ثم الإدراج ثم استهلاك الرمز ضمن معاملة واحدة.

### مسار العمل الذري

```text
تحقق من session والوقت والحالة والاختيار
→ بناء حمولة بطاقة بلا رمز أو هوية
→ AES-GCM
→ إدراج البطاقة
→ تحديث الرمز من UNUSED إلى USED بشرط الحالة
→ كتابة حدث تدقيق منقح
→ Commit أو Rollback كامل
```

### الملفات المستهدفة

| الطبقة | الملفات |
|---|---|
| core | `tokens.py` و`polls.py` |
| crypto | `secure.py` |
| data | `repo.py` و`db.py` |
| web | `routes.py` |
| ui | نموذج بطاقة المصوّت وصفحة الإيصال |
| tests | integration وsecurity وe2e |

### اختبارات البوابة

1. بطاقة صحيحة تعطي إيصالًا عشوائيًا ولا تعرض الاختيار لاحقًا.
2. فشل الإدراج لا يستهلك الرمز.
3. فشل التحديث لا يحفظ البطاقة.
4. طلبان متزامنان للرمز نفسه: ينجح واحد فقط.
5. لا توجد صلة بين صف البطاقة وصف الرمز في Schema أو payload أو logs.

## 12. المرحلة 9 — الإغلاق والعد والتدقيق

### الهدف

إغلاق التصويت بطريقة نهائية، ثم عد البطاقات السليمة، وعزل الفاسد، وتوقيع التقرير.

### مسار العمل

```text
OPEN → CLOSED → التحقق من Hash Chain → فك البطاقات والتحقق منها
→ عد الصالح → عزل الفاسد → إنشاء التقرير → RSA-PSS → TALLIED
```

### نقاط الضبط

1. العد لا يبدأ قبل `CLOSED`.
2. العد Idempotent؛ إعادة الطلب لا تنتج تقريرًا جديدًا أو نتيجة مختلفة.
3. بطاقة معدلة لا تحذف؛ تعزل مع سبب تقني غير كاشف.
4. التقرير لا يحوي بطاقة فردية أو رمزًا أو هوية.
5. صفحة المراجع تتحقق من توقيع التقرير بالمفتاح العام.

### اختبارات البوابة

| الاختبار | النتيجة المطلوبة |
|---|---|
| تقرير معدل | `INVALID` |
| سلسلة تدقيق مكسورة | `BROKEN` مع أول حدث متضرر فقط |
| بطاقة ذات tag غير صحيح | لا تعد وتدخل الحجر |
| إعادة العد | يعيد التقرير نفسه |

## 13. المرحلة 10 — الواجهة وتجربة الاستخدام

### الهدف

إكمال الصفحات بعد استقرار النواة، حتى لا تصبح الواجهة مصدرًا لقواعد مخفية أو تكرار منطق النظام.

### الشاشات بترتيب التنفيذ

1. دخول المشرف.
2. لوحة الاستطلاعات ومسودة الإنشاء.
3. صفحة المراجعة والنشر وتوليد الرموز.
4. صفحة المصوّت: الرمز ثم البطاقة ثم الإيصال.
5. صفحة الإغلاق والنتيجة.
6. صفحة التقرير والتحقق للمراجع.
7. صفحات الخطأ والفراغ والتحميل.

### معايير الواجهة

| المجال | المعيار |
|---|---|
| العربية | اتجاه RTL، صياغة مفهومة، رسائل لا تكشف أسرارًا |
| المصوّت | ثلاث شاشات كحد أقصى: رمز، اختيار، إيصال |
| الوصول | لوحة مفاتيح، label لكل حقل، focus مرئي، تباين جيد |
| الاستجابة | يعمل على 360px و1280px بلا فقد وظيفة |
| النتائج | لا تظهر إلا بعد `TALLIED` |

### اختبارات البوابة

اختبارات قبول للسيناريو الكامل، وفحص عرض الهاتف وسطح المكتب، وتجربة قارئ شاشة/لوحة مفاتيح، واختبارات أخطاء النماذج.

## 14. المرحلة 11 — المختبر الأكاديمي والخوارزميات

### الهدف

إضافة خوارزميات المقرر **بعد اكتمال مسار التصويت الحقيقي**، ضمن مختبر مستقل يشرح الاختلافات ولا يخلطها بأمن التشغيل.

### الترتيب المقترح للخوارزميات

| الترتيب | الخوارزمية | الهدف التعليمي | حالة الاستخدام |
|---:|---|---|---|
| 1 | Caesar | أبسط إحلال وتجربة القوة الغاشمة | بطاقة نصية تجريبية |
| 2 | Monoalphabetic | نمط التكرار وتحليل التردد | نص تجريبي |
| 3 | Vigenère | مفتاح متكرر وإحلال متعدد | نص تجريبي |
| 4 | Affine | العلاقة الرياضية وmodular inverse | نص تجريبي |
| 5 | Playfair | تشفير الأزواج | نص تجريبي |
| 6 | Hill | المصفوفات وmodulo | نص تجريبي محدود |
| 7 | DES3 | مقارنة تاريخية مع AES | مقارنة تجريبية فقط |
| 8 | AES | مقارنة بالخيار التشغيلي | نموذج منفصل عن البطاقات الحقيقية |
| 9 | RSA | المفتاح العام والتوقيع | توقيع رسالة مختبرية |
| 10 | Diffie-Hellman | إنشاء سر مشترك وليس تشفير رسالة | محاكاة طرفين |

### قاعدة منع التلخبط

كل خوارزمية في المختبر تعرض كنشاط **مستقل**. لا تُسلسَل الخوارزميات تلقائيًا فوق بعضها. إذا أضيفت تجربة «سلسلة»، تكون اختيارية وصريحة، وتعرض ترتيبها ومخرجات كل خطوة، ولا يسمح لمسار التصويت باستدعائها.

### اختبارات البوابة

1. كل تجربة تشفير/فك تعيد النص الأصلي عند المفتاح الصحيح حيث ينطبق ذلك.
2. المختبر لا يستورد مستودعات البطاقات أو مفاتيح التشغيل.
3. التحذير التعليمي ظاهر في كل تجربة كلاسيكية وDES3.
4. لا تُذكر الخوارزميات الكلاسيكية في إعدادات حماية الاستطلاع.

## 16. آلية العمل اليومية المقترحة

لكل مرحلة تنفيذية لاحقة نتبع الدورة نفسها:

```text
اقرأ المتطلب → حدّد الملفات المتأثرة → اكتب الاختبار أولًا أو معه
→ نفّذ أصغر تغيير → شغّل الاختبارات → راجع الأمان
→ حدّث التوثيق وtodo → احفظ نقطة مراجعة
```

ولا نفتح أكثر من مسار حساس في الوقت نفسه. مثال: لا نبدأ بالواجهة أو المختبر الأكاديمي بينما معاملة بطاقة التصويت غير مثبتة بالاختبارات.
